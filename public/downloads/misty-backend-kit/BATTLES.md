# Battles: backend specification (kit 1.2, 19 October 2026)

For the developers of the main site. Battles run on the same committed-seed engine as single opens. This file is the
rule book; `battles-reference.ts` is the server flow; `schema-battles.sql` the tables; `openapi.yaml` the endpoints
under `/v1/battles`; `test-vectors-battles.json` the results your implementation must reproduce byte for byte.

Configuration lives in the admin panel. Players only create, join, watch and verify battles inside the limits the
admin set. Nothing about odds, boxes, modes, fees or bots is decided on the client.

## 1. What a battle is

- N seats (2 to the admin's maximum) open the same box in each round; the admin's catalogue decides which boxes are
  eligible. A battle of 3 rounds with boxes A, B, A means every seat opens A, then B, then A.
- Entry per seat = the sum of the round prices plus the admin's fee, paid in credit when the seat is taken. The credit is
  held, not spent, until the battle starts; it is refunded if the battle is cancelled or expires.
- Every pull is a normal open: digest = HMAC-SHA256(`DRAW-<slug>-<serverSeed>-<clientSeed>-<nonce>`, ""), roll = first
  13 hex / 2^52, read against the round's frozen table. Battles use the main table only: a bonus row pays its credits;
  free spins are not played in battles.
- One server seed per battle, generated and hashed when the battle is created; the hash is shown to every seat before
  anyone pays. The server generates a random client seed for each seat when it joins and stores it; players never enter one. After the battle
  starts, nothing that feeds a roll can change.
- Pull order is round-major, seat-minor. The nonce of a pull is its position: `nonce = round × seats + seat + 1`,
  rounds and seats counted from 0. The one extra roll a mode may need uses `rounds × seats + 1` and a client seed made
  of every seat's client seed joined with `|` in seat order, so no single player controls it.
- Values are integer cents. Items count at their listed value; credit rows at the configured face (100 cents per
  credit by default).

### Modes

| Mode | Winner | Pot |
|---|---|---|
| normal | highest total over all rounds | every item and credit pulled, to the winner |
| crazy | lowest total | same |
| terminal | highest pull in the last round | same |
| jackpot | drawn in proportion to totals (extra roll) | same |
| group | everyone | split equally; odd cents to seat 0 |
| break | everyone | each seat keeps its own pulls; no pot |
| coinflip | one fair extra roll; no boxes | entries × seats × (1 − disclosed edge) |

Ties in normal, crazy and terminal are broken by the extra roll among the tied seats in seat order:
`winner = tied[floor(roll × tied.length)]`. Jackpot with every total zero falls back to a uniform draw.

### Payout

The winner receives the actual items and credits that were pulled: an `item_awards` row per item (ship or trade in,
as a single open) and a ledger entry for the credits. Group splits by value as credit unless the admin enables item
allocation; break hands each seat its own pulls. Coinflip pays credit. The house keeps nothing extra: its margin is the
boxes' return, which the admin set. If the admin enables a battle fee, it is a disclosed percentage added on top of
the box prices (entry = prices + fee), kept by the house, never part of the pot, and shown on the battle page.

### Bots

Off by default. If the admin turns them on, the creator of an `open` battle that nobody joins can ask for bots
(`POST /v1/battles/{id}/bots`): the server fills every free seat with a bot from the admin's list, the battle becomes
`full` and the countdown starts. A bot is a name and a picture, nothing more. It plays with the same tables and the
same committed seed, its client seed is generated by the server and recorded as `bot`, it holds no credit, and what
it wins returns to the house (no award, no ledger entry). A bot seat is labelled as a bot on every screen, in the
lobby and in game history. A bot that plays with better odds than players is a rig; the engine does not support it and
the licence forbids it. This is also how Evocase described its bots on 15 October: "just names and images, no higher
configuration", and a player can "ask bots to join" when nobody else does.


## 2. The state machine

| Status | Meaning | Allowed next |
|---|---|---|
| `open` | created, seats free, credit held for taken seats | `full`, `cancelled`, `expired` |
| `full` | every seat taken; countdown running | `in_progress`, `open` (a seat left before the start), `cancelled` |
| `in_progress` | the server is resolving rounds and writing pulls | `settling` |
| `settling` | pulls written; awards and ledger being committed | `finished` |
| `finished` | settled; seed revealed; verifiable | none |
| `cancelled` | creator or admin cancelled before the start; entries refunded | none |
| `expired` | never filled within the admin's window; entries refunded | none |

Screens show plain words, not the codes: `open` and `full` show as "Waiting", `in_progress` and `settling` as
"Ongoing", `finished` as "Settled", `cancelled` and `expired` as their own words. "Settled" means the money has moved:
the awards and ledger entries exist. The code stays in the API and in the database.

Rules the server enforces:

- Every transition is one UPDATE guarded by the current status and a `version` counter (`WHERE id = ? AND status = ?
  AND version = ?`); zero rows updated means someone else moved first, and the caller re-reads. Never set a status
  without that guard.
- `start` runs once. It is idempotent on the battle id: a retry while `in_progress` returns the stored state; a retry
  after `finished` returns the result.
- Rounds are resolved inside one transaction per battle (or one per round with the battle row locked), written to
  `battle_pulls` before any payout; `settling` writes awards and ledger entries and only then moves to `finished` and
  reveals the seed. A crash between `in_progress` and `finished` is resumed by a sweeper that re-runs the
  deterministic resolution (same inputs, same result) and completes settlement; nothing is ever re-rolled.
- Credit movements are ledger rows with reasons `battle-entry` (hold), `battle-refund`, `battle-win`, `battle-fee`;
  balance is the sum. The hold is taken at join, so a player cannot hold a seat with money they then spend elsewhere.
- Expiry and countdown are server timers (a job every few seconds), never a client timer. The client only displays
  what the server says.
- Every transition writes a `battle_events` row (who, what, when, from, to) for the audit log and for the live feed.

## 4b. The lobby and rooms

A battle is a room. Creating a battle opens a room in the lobby; other players join its free seats; it starts when
every seat is taken.

- The lobby lists public battles that are `open` (Waiting), plus recent `in_progress` (Ongoing) and `finished`
  (Settled) ones so players see activity. Each row shows: mode, the boxes per round with prices, entry per seat, the
  seats (name and picture per taken seat, bots labelled, free seats empty), the creator, how long ago it opened, the
  secret hash, and a Join button with the entry on it. Ongoing rows show "rounds playing"; settled rows show the winner
  and the pot.
- The list comes from `GET /v1/battles` and stays live through the lobby stream `GET /v1/battles/events`: room
  opened, seat taken, seat left, status changed, room settled. The client never invents a row.
- Join: a player takes the first free seat with `POST /v1/battles/{id}/join`; the hold and the seat are one
  transaction; the player can sit in any seat, not only seat 0; the room view opens at once and follows
  `GET /v1/battles/{id}/events`.
- Leave before the start refunds the hold (`POST /v1/battles/{id}/leave`); a full room goes back to open. The creator
  cannot leave; they cancel while alone. After the start nobody can leave.
- Create: the player picks mode, seats and one box per round from what the admin allows, and may make the room
  private (invite code). The creator takes seat 0 and pays the hold; the room appears in the lobby with its hash.
- Ask bots to join: only the creator, only while open, only if the admin has bots on; every free seat gets a bot.
- Private rooms are not listed; they are joined with the invite code.
- "Your battles" above the lobby: battles played, won, spent, took home, from `GET /v1/battles?mine=true` and the
  `battle_history` view.

## 3. What the admin panel configures

| Setting | Meaning | Default |
|---|---|---|
| battles enabled | master switch | off |
| modes allowed | subset of normal, crazy, terminal, jackpot, group, break, coinflip | normal, crazy, terminal |
| seats allowed | e.g. 2, 3, 4 | 2, 3, 4 |
| rounds max | boxes per battle | 10 |
| eligible boxes | from the catalogue; each with its current table and bonus versions | none until chosen |
| fee percent | disclosed fee on entries, 0 to 20 | 0 |
| coinflip edge | 0 to 10% | 0 |
| open battle expiry | minutes an `open` battle waits before `expired` | 30 |
| countdown seconds | from `full` to `in_progress` | 5 |
| private battles | invite code instead of the public list | on |
| bots | off, or on with labelling text | off |
| max concurrent battles per player | anti-abuse | 3 |
| credit face cents | what one credit counts for in totals | 100 |

Changing a setting never touches an existing battle: the battle pinned its boxes' table hashes, its mode, its fee
and its seats at creation.

## 4. What the client does

(The lobby is section 4b.)

Players, with their credit balance: list open battles; create one within the admin limits (mode, seats, rounds from
the eligible boxes, public or private); join a seat (the hold is taken); leave before the start (hold released);
watch the rounds play back from the server's records; see the result, their awards and their ledger; open the verify
page. Spectators watch public battles. Nothing is computed on the client: the animation starts after the server's
pull records arrive and ends on exactly what they say.

## 5. API (summary; the contract is in openapi.yaml)

| Method | Path | Does |
|---|---|---|
| GET | /v1/battles | the lobby: public battles, filter by status; `mine=true` for the caller's own |
| GET | /v1/battles/events | the lobby stream: room opened, seat taken, seat left, status changed, settled |
| POST | /v1/battles | create within admin limits; returns the server hash, seat 0 taken by the creator with a hold |
| GET | /v1/battles/{id} | the battle as it stands; pulls appear as rounds resolve; seed only when finished |
| POST | /v1/battles/{id}/join | take a seat; the server generates its seed; idempotent on an idempotency key |
| POST | /v1/battles/{id}/leave | before the start; releases the hold |
| POST | /v1/battles/{id}/cancel | creator before anyone else joined, or admin any time before the start; refunds |
| POST | /v1/battles/{id}/bots | creator asks bots to fill the free seats (admin bots on); battle becomes full |
| GET | /v1/battles/{id}/events | server-sent events: seat joined, countdown, round resolved, finished |
| GET | /v1/battles/{id}/verify | public, stateless recomputation with one boolean per claim |
| GET | /v1/admin/battles/settings, PUT | the settings above |
| POST | /v1/admin/battles/{id}/cancel | admin cancel with refund and a reason |
| GET, PUT | /v1/admin/battles/bots | the bot list: name and picture |
| GET | /v1/admin/battles/report | battles played and GGR per day and mode |

`start` is not an endpoint: the server starts the battle when the last seat is taken and the countdown ends (or at
once when the admin's countdown is 0).

## 6. Security checklist

- Server seed from a CSPRNG per battle; stored encrypted; revealed only at `finished`.
- Commit before pay: the hash is in the create response and on the battle page before any seat is taken.
- Seat seeds generated by the server (CSPRNG) at join and stored before the start; no endpoint sets or changes one.
- Nonce map fixed by position; no client input after the start influences any roll.
- One seat per player per battle; one player cannot join as two seats; a bot seat is never a player's.
- Holds, not optimistic balances: join debits the hold inside the same transaction that takes the seat; insufficient
  credit fails the join, never the battle.
- Idempotency keys on create, join, leave and cancel; a retried join returns the same seat.
- Status guard plus version on every transition; the resolution is deterministic, so a crash resumes without
  re-rolling.
- Awards and ledger entries written before `finished`; the seed is revealed only after they are committed.
- Rate limits: creates per minute, joins per minute, concurrent battles per player (admin setting).
- Ownership checks on leave and cancel; admin actions carry a reason and an audit row.
- Private battles by invite code; codes are random, 10 characters or more, single use per seat.
- Live updates come from the server's records (events table), never from client messages.
- Verify page recomputes in the browser from the revealed seed, the seat seeds and the frozen tables fetched by hash.
- Logs: every transition, every pull, every payout, with the battle id; no secrets in logs.

## 7. Data (see schema-battles.sql)

`battle_settings` (one row per site), `battle_bots` (name, picture), `battles` (status, version, mode, seats, rounds as a JSON array of
`{slug, tableHash, bonusHash, priceCents}`, fee, server seed encrypted, server hash, created by, timestamps per
transition, winners, pot, shares), `battle_seats` (seat number, player or bot, the server-generated seed and its source, hold ledger
id, joined at), `battle_pulls` (round, seat, nonce, digest, roll, outcome id, value cents, credits), `battle_events`
(audit and feed). The ledger and `item_awards` are the existing tables with new reasons.

## 8. History and reports

- A player's game history lists every battle they sat in with their pulls, the result and what they took home, next
  to their single opens: `battle_seats` joined to `battle_pulls` by player. The admin's player screen shows "Boxes
  opened" and "Battles played" counters from the same tables.
- The admin dashboard shows battles played per day and per mode, and the gross gaming revenue (GGR) per game mode:
  player entries kept minus what players took home. For battles: GGR = (`battle-entry` − `battle-refund`) −
  `battle-win` − listed value of item awards from battles. Bot seats are not player money. The view `battle_daily_report` in `schema-battles.sql` does
  this arithmetic per day and mode.
- A finished battle is never edited; its seats, pulls, events and seed are kept as long as the ledger is kept.

## 9. Where battles sit in the codebase

Battles are their own module: tables prefixed `battle_`, one backend module, one timer job, one set of routes under
`/v1/battles`. They touch the rest of the system in four places only: the ledger (holds, refunds, wins, fees), item awards (what the winner takes home), boxes and frozen tables fetched by hash, and the site's auth.
Nothing else reads battle tables. That keeps the module out of the first build (single opens, credit, admin panel)
and lets it move to a separate service later without touching the core.

## 10. Conformance

1. Reproduce every case in `test-vectors-battles.json`: pulls, totals, winners, shares, extra roll.
2. Property test: 10,000 two-seat normal battles on the Timepiece table; each seat wins 50% ± 2 points; the pot
   equals the sum of pulls every time.
3. Concurrency test: 50 clients join the same 2-seat battle at once; exactly one succeeds per seat; every loser's
   hold is released; no duplicate seats.
4. Crash test: kill the process between `in_progress` and `finished`; the sweeper completes the battle with the same
   pulls (compare digests) and exactly one payout.
5. Replay: for 1,000 finished battles the verify endpoint reproduces winners, totals and every pull.
6. Bots: a battle won by a bot writes no award and no ledger entry; a battle won by a player against bots pays the
   player in full; the report counts only the player's entry.

The simulator runs the pure parts in `scripts/smoke-battles.ts` and plays this exact logic at /operators/vendor,
Battles tab (Admin panel button for the settings). Plain-language page: /docs/battles. Developer page: /docs/battles/dev.
