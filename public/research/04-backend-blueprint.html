0. The short version

  1. The odds engine is small; everything around it is the work. Drawing an item from a weighted table is twenty lines. Making it provably honest, concurrent, auditable, priced correctly and legal is the system.
  2. Get the arithmetic right once. Odds as integer tickets out of a fixed total, never floating-point percentages. Draw with a hash wide enough that modulo bias is negligible, or use rejection sampling. Two of the audited operators get this subtly wrong (section 2.2).
  3. Commit before you draw. The box manifest (items, odds, prices, cash-out rate) and the server seed are fingerprinted and published before any open. The result is a deterministic function of the manifest, the server seed, the player's seed, a public beacon value and a counter. Anyone can recompute it.
  4. Money and inventory are the hard parts. A double-entry ledger, idempotent operations, serializable transactions on finite pools, frozen prices between commit and cash-out, and a fulfilment flow for the few items people actually ship.
  5. What is still missing before a spec can be written is listed in section 6: jurisdiction and legal framing, the price-data contract, the inventory model, the v1 product list, and the identity/KYC provider. Payments are deferred by your decision.

2. The odds engine, precisely

2.1 Representing odds

  • Each item's odds are an integer weight out of a fixed ticket total T (for example T = 100,000,000). A 0.5% item has weight 500,000. Percentages and floats are display only.
  • Invariant: weights sum to exactly T. Reject any box version that does not. Misty's tables sum to 100.15% and 100.09% because they were composed in percentages; integer tickets make that impossible.
  • Minimum weight is 1 ticket, so the rarest possible item is 1 in T. Choose T so that the rarest item we are willing to offer is representable and so that T is far smaller than the hash range (section 2.2).
  • Ranges are cumulative and ordered: item k owns tickets [c(k-1), c(k)) where c is the running sum in a published, fixed order. Publish the ranges, not just the weights, so a verifier needs no ordering rules.

2.2 Drawing a ticket without bias

The draw converts a hash into a ticket number. The naive conversion is biased:

  • Modulo bias. Taking the first 8 hex characters (32 bits, 4,294,967,296 values) and reducing to 100,000,000 tickets, as Packs.com documents, cannot be uniform: 4,294,967,296 is 42 × 100,000,000 plus 94,967,296, so 94,967,296 tickets are reached by 43 source values and the other 5,032,704 by 42. The unlucky tickets are each about 2.4% rarer than stated. If the reduction is a modulo, the unlucky tickets are the last 5% of the table, so whatever items sit there are 2.4% rarer than advertised; if it is a floor-scaling, the unevenness is spread across the table and only matters for items with very few tickets. Packs.com does not say which it uses. Either way it is measurable over millions of opens and avoidable for free.
  • Fixes. Use the full hash as a 256-bit integer and reduce modulo T (bias of about T / 2^256, nothing), which is what Jemlit does; or take 64 bits and apply rejection sampling (discard values above the largest multiple of T); or use a floating division only for display, never for the draw.
  • Reference draw:
message   = client_seed + ":" + beacon_round + ":" + beacon_value + ":" + nonce
digest    = HMAC_SHA256(key = server_seed, message)        # 256 bits
ticket    = int(digest, 16) mod T                          # bias ~ T / 2^256
item      = the item whose range contains ticket           # binary search over cumulative ranges
  • Use HMAC with the server seed as the key and every other input in the message, in a fixed, documented order with unambiguous separators. Document whether strings are bytes of UTF-8 and whether numbers are decimal text. Verifiers fail on exactly these details (Misty's published snippet confused even us).

The beacon closes the two attacks found in the Fair Casino audit (server-generated client seed; server choosing its seed after seeing the client's): the operator cannot know the beacon value when it commits, and the player cannot either. drand's fast chain publishes a value every 3 seconds, which sets a floor on reveal latency; the UI can animate through it. A blockchain block hash (EOS at Razed and PackDraw) is the alternative; it needs a rule for which block counts and what happens on a fork or a stalled chain. Specify the fallback (wait, or cancel and refund) and never fall back to "operator picks".

2.4 The manifest and the commitment

manifest = {
  "box_id": "...", "version": 7,
  "ticket_total": 100000000,
  "items": [ {"item_id": "...", "weight": 500000, "range": [0, 500000],
              "retail": 16400.00, "asking": 15200.00, "realized": 13950.00,
              "realized_confidence": "high", "cashout": 13950.00 }, ... ],
  "cashout_rule": "realized price at commit time, paid in fiat",
  "price_snapshot_at": "2026-10-10T12:00:00Z",
  "valid_until": "2026-10-17T12:00:00Z",
  "beacon": {"source": "drand", "chain": "quicknet"},
  "hash_alg": "SHA-256", "draw_alg": "HMAC-SHA256 mod ticket_total"
}
commitment = SHA256(canonical_json(manifest))
  • Canonical JSON: sorted keys, no insignificant whitespace, integers for money in cents (no floats anywhere in the manifest; floats serialize differently across languages and break hashes).
  • The commitment is published on the box page and in the daily log before the version can be sold.
  • Prices are frozen in the manifest. The cash-out a player receives is the manifest's number, however the market moved. A manifest therefore has a valid_until; after that a new version with fresh prices is committed.
  • Daily log root: every open's record (open id, manifest hash, server seed hash, client seed, beacon round, nonce, ticket, item) is a leaf; publish the Merkle root daily and give each player their inclusion path. Keep the leaves available for download so a third party can rebuild the root.

2.5 Finite pools (kuji) are a different algorithm

  • Odds are the remaining inventory, not a weight table. The manifest lists the full inventory; each sale decrements it; the box page shows remaining counts live.
  • Draw without replacement: ticket space equals remaining items; the mapping changes after every sale, so the proof must include the inventory state (a hash of the remaining list) at draw time.
  • Concurrency: two players buying at the same instant must not both receive the last grail. Either a serializable transaction per pool or a single-writer queue per pool. Reservations with a short TTL if payment confirmation is asynchronous.
  • Closure rule (suggested in principle in the plan): a pool is not closed by the operator before it sells out. If it must close, the undrawn top items are drawn among the buyers (on the beacon) or all buyers are refunded. Encode this in the manifest so it is a promise, not a policy.

2.6 Battles

  • One beacon round per battle round, shared by all players, so results are comparable and nobody can re-roll.
  • Settlement by committed prices (the manifest's realized values), not by live prices.
  • Bots. Either none, or disclosed and bound to the same odds and prices, with their outcomes in the same public log. Undisclosed bots are the house playing against the player; the vendor's platform ships that by default.

2.7 Economics guardrails inside the engine

  • At manifest creation, compute EV at retail, asking and realized. Refuse to publish if realized EV is outside the policy band (for example, between 85% and 100% of price for flagship boxes, whatever the floor decision is).
  • Store the three EVs in the manifest so they are part of the commitment and can be shown.
  • Alert when observed outcomes drift from stated odds beyond statistical tolerance (section 5.9).

4. Service boundaries and the minimum stack

  • Separation that matters: the randomness and commitment service holds seeds and signs proofs; the back office cannot call its "draw" function directly; price overrides go through the pricing service with four-eyes approval and an audit entry. The point is that no single admin can change a table, a price or a seed quietly.
  • Idempotency everywhere money moves: a client-supplied idempotency key on open, buyback and payout; retries return the same result.
  • Secrets: server seeds generated by a cryptographically secure generator, encrypted at rest with a KMS or HSM-backed key, revealed only through the reveal path after the open is final.
  • Public verifier: a static page plus a tiny open-source script (we already have the seed of it in tools/verify_roll.py) that takes a manifest, seeds, beacon and nonce and reproduces the item. If the verifier needs our API to work, it is not independent.
  • Language and database are free choices; what is not free: integer money, serializable transactions on pools and ledger, append-only tables for prices, openings and audit.

5. Complications and problems to expect

Grouped by where they bite. The ones marked ★ are the ones most teams get wrong first.

5.1 Correctness of the draw

  • ★ Floating-point odds that do not sum to one; percentages composed by hand (Misty).
  • ★ Modulo bias from a 32-bit slice of the hash (section 2.2).
  • Ordering ambiguity: the same weights in a different order give different results; publish ranges.
  • Encoding ambiguity in the HMAC message (separators, UTF-8, number formatting).
  • Reusing a nonce after a seed rotation, or not resetting it when the spec says to.

5.2 Concurrency and money

  • ★ Double spend on the wallet under concurrent requests; fix with a ledger and database-level constraints, not application checks.
  • Exactly-once draw per paid open: payment confirmed, draw crashed, player retries. Idempotency keys and a state machine (paid → drawn → revealed → settled) with recovery.
  • Finite pool races on the last item (section 2.5).
  • Partial failures between ledger and inventory; use one transaction or a saga with compensation and a reconciliation job.

5.3 Commitment and reveal

  • Revealing the seed before the open is final lets a player abandon unfavourable results; reveal only after the state machine reaches "revealed".
  • Beacon latency (3 seconds on drand's fast chain) and beacon outages: the fallback must never be "operator picks"; cancel and refund is acceptable, and the rule is published.
  • Manifest changes after publication: forbidden; new version, new hash, old version honoured until valid_until.
  • Canonicalization bugs: two languages serializing the same manifest differently; test the hash against a fixed vector in CI.

5.4 Valuation

  • ★ Prices move between commit and cash-out; freeze them in the manifest and accept the market risk, or shorten valid_until.
  • Thin comps for rare items: the confidence band is low, the number is a guess, and the box's EV inherits the uncertainty. Policy: no item with low-confidence price in a box whose EV depends on it.
  • Data licensing: WatchCharts needs a distribution licence to display; eBay sold data is gated; scrapers are research-only. The comps engine must record the source per price so licensed and unlicensed data never mix.
  • Identity mismatch: the catalogue's "Rolex 126610LN, 2023, full set" must map to the same identity the price source uses, including condition.

5.5 Inventory and fulfilment

  • Item revealed but no longer in stock (sold on another channel): only commit items you hold or have reserved by contract; StockX simply marks the tier out of stock.
  • Authentication: every item certified before it enters a manifest; recheck before shipping; keep certificates.
  • Shipping high-value goods: insurance, signature, customs if ever outside the US, loss claims; title and risk transfer wording. Only about 200 items a month ship even at large operators, so this can be manual at first, but it cannot be sloppy.
  • Returns and disputes: a revealed item is a completed sale under most terms; decide the policy and the chargeback stance before launch.

5.6 Security and insider risk

  • ★ The operator is the main threat model. Four-eyes on box versions and price overrides; hash-chained audit log; seeds in a KMS; no "god mode" in the back office.
  • Seed leakage through logs, error messages or backups.
  • Client seed defaults chosen by our code: display it, let the player change it, and still mix the beacon so the default does not matter.
  • Admin accounts, bots and streamer accounts must have no special code paths; if they exist for marketing, they are labelled and in the public log.

5.7 Fraud and abuse

  • Bonus abuse and multi-accounting (free boxes farmed across accounts).
  • Card fraud and chargebacks on deposits; stolen-card buyers cash out instantly. Delays or KYC tiers on cash-out are the standard answer and conflict with "cash by default", so design the tiers early.
  • Collusion in battles; sybil players.

5.8 Compliance (US web app)

  • Geo-fencing by state; the legal framing (purchase of an asset vs promotion) decides whether a free-entry route is needed. Deferred with payments but it shapes the data model (free entries must share the same draw).
  • Age gating at 18 or 21 depending on framing and state; KYC tiers tied to cash-out thresholds.
  • Sanctions screening; self-exclusion and spend caps (Omaze's monthly cap is a reasonable model).
  • Privacy: CCPA at minimum; data retention for proofs (indefinite) versus personal data (limited).
  • Tax: prize reporting thresholds if the framing is a promotion; sales tax on shipped goods; records for both.
  • Odds disclosure wording must match the manifest exactly; the FTC Act §5 exposure is in the gap between the two.

5.9 Testing and observability

  • A simulation harness that opens each box version millions of times with the real draw code and checks observed frequencies against the manifest (chi-square), EV against the stored EVs, and the modulo-bias test.
  • Property tests: weights sum to T; ranges contiguous; canonical hash stable across languages; verifier reproduces every open in a sample.
  • Drift monitor in production: observed vs stated odds per box version, published on the transparency page. This is also the thesis's detectability experiment, run on ourselves.
  • Reconciliation: ledger sums, inventory counts, daily root rebuilt from leaves.
