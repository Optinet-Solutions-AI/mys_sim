1. Purpose and principles

What it is. A research sandbox that reproduces the mechanics of mystery-box platforms so we can test how different algorithms and settings behave, reproduce the manipulations documented in the research, and generate data for the thesis and for our own design decisions. It is not a product: no real money, no registration, no real players. Every participant is a simulated agent (a bot).

What it grows into. A feature hub. Each operator we audited has mechanics worth testing on the same agents, the same catalogue and the same metrics: IcyBox's finite drops and undisclosed buyback, Jemlit's cashback haircut and "guaranteed" tiers, StockX's tier-first draw and value floor, Courtyard's expected-value pricing and public pull log, Misty's credits-as-raffle-entries, Cases.gg's disclosed edge and auto-rotation, and our own Glass Box ideas. We start with the vendor's four features because they are the industry's default. We add the others wave by wave, as labs or as options inside existing labs, and the comparison across all of them is part of the research: it is how we decide which features are best, by evidence rather than by taste.

Principles.

  1. Isolation. Each lab (Mystery Boxes, Sell-back, Battles, Retention) has its own configurations and runs. Nothing in one lab reads or changes another. The item catalogue is the one shared resource, read-only, and each run keeps its own copy of the items it used.
  2. Immutability. A run snapshots its full configuration and the catalogue items it used. Editing a configuration afterwards creates a new version; earlier runs never change.
  3. Reproducibility. Every run has a seed. Same snapshot plus same seed gives the same results, bit for bit.
  4. Honesty is a setting. Provably fair, commitment, beacon and rotation can be switched on, off, bypassed or rigged, so the same box can be run the way the vendor runs it, the way we would run it, and the way a cheat would run it, and the three can be compared.
  5. Everything documented. Each algorithm and each rig has a documentation page generated from its metadata. Each run stores config, results and a report. The tracker logs every milestone.

2.2 How we decide what is "best"

The hub exists to make the decision by evidence. Every feature is scored on the same metrics, from the same agents and catalogue:

LensMetrics
FairnessCan an outsider verify it; which rigs it is vulnerable to; sample size needed to detect cheating
Honesty of valueStated RTP versus realized RTP at each price layer; gap between displayed and cash value
Player harmRuin rate; chasing behaviour; money that can never leave; bonus-driven overspend
Operator economicsHold, GGR, NGR, shipped items, bonus cost, under honest and under rigged settings
Regulatory exposureWhich rules in dossier 1 §4 and dossier 2 §5 the feature would trip
ComplexityEngine and operations effort; failure modes from dossier 4 §5

The output is a scorecard per feature and per combination, which becomes a thesis chapter and the basis of the Glass Box product decisions.

3. Agents (the bots)

All players are agents with explicit, documented policies. Populations are generated from parameter distributions so that "1,000 players" means 1,000 agents with varied but reproducible behaviour.

4. Architecture

simulator/
  app/                 Next.js (App Router) pages: catalogue, labs, runs, docs
  engine/              pure TypeScript, no I/O: rng sources, mappings, tables, commitments, rigs, agents, metrics
  workers/             Web Worker entry for in-browser runs (up to about 1,000,000 events)
  server/              Node route handlers for large runs with streamed progress
  supabase/            SQL migrations, seed data (catalogue), storage policies
  docs/                Markdown rendered in-app: labs, algorithms, rigs, research dossiers (copied from research/)
  • Engine is pure. It takes a snapshot and a seed and returns events and aggregates. It runs identically in the browser worker and on the server, which is what makes results reproducible and the verifier trustworthy.
  • Small runs in the browser, large runs on the server. A Web Worker keeps the UI responsive up to roughly a million events; above that a server route streams progress and writes aggregates to Supabase. Caps are configurable; v1 caps at 10 million events per run.
  • Supabase holds configurations, run snapshots, aggregates, a capped sample of raw events, and the catalogue. No auth in v1 (single-researcher tool); the schema is written so row-level security can be turned on later.
  • Randomness for simulation versus randomness under test. Agents and populations use a fast seeded PRNG (xoshiro or sfc32) so runs are reproducible. The algorithm under test uses whatever it specifies, including real SHA-256 and HMAC via the Web Crypto API, and a recorded or live drand beacon.
  • Icons and "images": see section 6. No binary image generation; items render as an icon on a coloured tile.

5. Isolation and immutability rules (the contract)

  1. A config belongs to exactly one lab. Copying a config into another lab is a deliberate action that creates a new config there.
  2. Starting a run freezes: the config, the catalogue items it references, the algorithm versions, the rig settings, the agent policies and the seed. All of it is written into the run before the first event.
  3. Editing a config creates version n+1 with parent_id pointing at n. Runs reference the version they used.
  4. Deleting a config does not delete its runs. Runs are deleted only explicitly, and the deletion is logged.
  5. A run's results are written once. Re-running creates a new run.
  6. The catalogue is editable, but items are versioned too: editing an item creates a new item version, and old runs keep the version they used.
  7. Comparisons are only offered between runs of the same lab.

6. Catalogue and icons

6.1 Items

About 48 starter items spread to mirror the real drop tables we captured: many fillers under $15, a middle band from $50 to $2,000, and a few grails from $5,000 to $30,000. Each item has:

  • name, brand (fictional by default, for example "Montvale", "Maison Arlet"; a switch to real names as text only if you want them), category (watch, bag, jewellery, sneaker, accessory, credit/voucher),
  • tier (filler, common, rare, epic, legendary, grail),
  • three prices in cents: retail, asking, realized, with a confidence (high, medium, low),
  • icon (an icon reference, see below) and a tile color.

Prices are illustrative but shaped like the research: realized below asking, asking below retail for most brands, and the Hermès-style exception where realized exceeds retail for a couple of rationed bags.

Detector panel. For any run, the simulator runs the honest verifier on a sample, the chi-square test of observed versus stated odds, realized RTP against stated RTP at each price layer, cohort comparisons (tagged accounts, default versus custom seeds, bots versus humans), drift and change-point tests, and reports which rigs would have been caught, at what sample size, and which would not. This is the detectability experiment from dossier 1 §6 made interactive.

Ethics and scope. The rigs run only against the simulator's own engine. Nothing connects to a live operator. The documentation describes mechanisms and detection, which is the standard security-research posture; the thesis chapter will present it as such.

9. Lab specifications

9.1 Mystery Boxes

  • Configure: items (from catalogue) with weights or an RTP target for the solver; box price; value layer used for RTP (retail, asking, realized); algorithm choices (randomness source, commitment scheme, ticket mapping, odds-table model); rigs; agent population (or "one open at a time" with no agent).
  • Run: N opens; seed; optional per-account tags.
  • Read: stated vs observed odds per item with chi-square p-value; realized RTP at each price layer; expected value; probability of an outcome worth at least the price; payout histogram; top-item hit log; bias map across the ticket range; verifier sample results; a run report.

9.2 Sell-back / Cart

  • Configure: sell-back rule (vendor: 100% of listed value to balance; or a haircut; or Glass Box: cash at realized); withdrawal rule (cash allowed, or only through items after wagering); agent population (deposit distribution, thresholds, re-bet fraction, stop rules); the box set they open (a config from the Mystery Boxes lab copied in, never linked).
  • Run: N agents, N sessions or N days; seed.
  • Read: hold as % of deposits; GGR and NGR; sell-back rate; ship rate and shipped items per period (compare with the vendor's "200 orders a month"); bankroll trajectories; time to ruin distribution; the effect of "withdraw through items" on how much money ever leaves.

9.3 Battles

  • Configure: boxes per battle; players per battle; mode (v1: highest total wins; others on request); entry price; bots on or off, timeout, bot odds policy; agent population; rigs.
  • Run: N battles; seed.
  • Read: average bet per battle versus single opens (the vendor's "higher average bet"); realized edge; winner distribution bots vs humans; variance of outcomes; share of total wager (the vendor's "90%" claim under different populations).

9.4 Retention

  • Configure: daily box tier schedule and expiry rule (24-hour no-stacking vs stacking); leaderboard races (cadence, prize tiers); affiliate rule (3 free boxes, % of referred deposits); bonus cost model (value of the drop); visitor population (visit probabilities, churn hazard, response to incentives). All assumptions labelled.
  • Run: N agents over N days; seed.
  • Read: retention curves (day 1, 7, 30); daily active agents; bonus cost versus incremental wagering; LTV; hold after bonuses; wager concentration in races.

Each lab page has three panes: Configure, Run, Results, plus a Docs tab that explains the lab, the selected algorithms and the active rigs.

10. Run lifecycle

  1. Create or pick a configuration (versioned).
  2. Start a run: choose sizes and a seed (or let the app pick one and show it). The snapshot is written.
  3. Execute: in the browser worker or on the server, with a progress bar and cancel. Partial results are not saved.
  4. Persist aggregates, charts data, verifier samples and a capped event sample.
  5. Report: metrics, charts, detector findings, and a Markdown report that can be exported.
  6. Compare: pick two or more runs in the same lab; the app shows metrics side by side and overlays charts.
  7. Export: JSON (snapshot + results), CSV (events sample, per-item table), Markdown (report).

Glossary

how surprising the observed table would be if the stated odds were true.

Agent
A simulated player with an explicit policy; what you called a bot.
Aggregate
A summary number computed over a run (for example, realized RTP), stored instead of every event.
Chi-square test
A statistical test of whether observed counts match stated probabilities; its p-value says
Config (configuration)
The full set of settings for a lab, saved as a version.
Detector
The panel that runs the honest verifier and statistical tests against a run to see which rigs are caught.
Engine
The pure TypeScript package that executes a run; no network, no database, same code in browser and server.
Rig
A switchable manipulation that reproduces a documented operator cheat inside the simulator.
Run
One execution of a config with a seed and sizes; immutable once written.
Seed (simulation seed)
The number that makes a run reproducible; not the same as a server seed in a commitment scheme.
Snapshot
The frozen copy of config, catalogue items and algorithm versions stored with a run.
Web Worker
A background thread in the browser so a long simulation does not freeze the page.
